# Supabase Production Setup — Gazak Go

## الهدف

تهيئة مشروع Supabase الحقيقي لتشغيل Gazak Go خارج وضع العرض التجريبي، مع الحفاظ على نفس دورة الطلب والصلاحيات والمخزون والإسناد الذكي الموجودة في المستودع.

## 1. إنشاء مشروع Supabase

أنشئ مشروع PostgreSQL جديد في Supabase.

بعد الإنشاء نحتاج القيم العامة التالية فقط للواجهة:

- Project URL
- Publishable/Anon Key

لا تضع Service Role Key داخل الواجهة أو في GitHub.

## 2. المشروع وقاعدة البيانات

تم إنشاء مشروع Supabase فعلي باسم `gazak-go`، وحالته `ACTIVE_HEALTHY`.

Project URL: `https://uxpzhhyqdbucfnsdtygq.supabase.co`

تم تطبيق جميع ملفات الـmigrations الموجودة حالياً في المستودع من `001` إلى `017` بالترتيب الرقمي، وتشمل الجداول وRLS وRPCs والمخزون ودورة الطلب وSmart Dispatch والإشعارات والمرتجعات والاستبدال والفواتير والدفع وتقوية صلاحيات تنفيذ الدوال وتحسين RLS.

## 3. إعداد Authentication

في Supabase Auth:

- فعّل Email/Password.
- فعّل Google OAuth فقط بعد إعداد بيانات Google الرسمية.
- اضبط Site URL على نطاق التطبيق الفعلي.
- أضف Redirect URLs للصفحة الرئيسية و`/reset-password`.
- فعّل تأكيد البريد حسب سياسة التشغيل التي تختارها.

## 4. الأدوار

الأدوار التطبيقية المعتمدة هي:

- admin
- distributor
- driver
- customer

يجب أن تكون صلاحيات الأدوار مبنية على RLS وسياسات قاعدة البيانات، وليس على إخفاء عناصر الواجهة فقط.

## 5. Edge Function

تم نشر `supabase/functions/admin-create-user` على المشروع الحقيقي بحالة `ACTIVE` و`verify_jwt=true`.

وظيفة إنشاء المستخدم الإداري تحتاج Service Role Key داخل بيئة Edge Function فقط، ولا يجب وضعه في المتصفح أو GitHub.

## 6. متغيرات الواجهة

في بيئة الاستضافة الإنتاجية:

```env
VITE_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
VITE_SUPABASE_ANON_KEY=YOUR_SUPABASE_ANON_KEY
VITE_DEMO_MODE=false
VITE_CARD_PAYMENTS_ENABLED=false
```

لا ترفع `.env.local` أو أي مفتاح سري إلى GitHub.

## 7. اختبار ما بعد الربط

اختبر بالترتيب:

1. تسجيل مستخدم جديد.
2. تسجيل الدخول والخروج.
3. استعادة كلمة المرور.
4. إنشاء طلب.
5. التحقق من حجز المخزون.
6. قبول الطلب وتجهيزه وجعله جاهزاً.
7. الإسناد الذكي للسائق.
8. منع تعارض السائق مع طلب جاري.
9. منع الإسناد الذي يسبب تأخيراً في نفس المسار.
10. بدء التوصيل والوصول والتسليم.
11. إلغاء الطلب والتحقق من إعادة المخزون.
12. الإشعارات.
13. الفاتورة وحالة الدفع.
14. اختبار RLS بحساب من كل دور.

## 8. الدفع الإلكتروني

لا تفعّل:

`VITE_CARD_PAYMENTS_ENABLED=true`

إلا بعد ربط بوابة دفع حقيقية، وتنفيذ webhook خادمي يتحقق من نتيجة الدفع ويستدعي RPC الخاص بتحديث حالة الدفع.

## 9. معيار إغلاق مرحلة Supabase

لا تُعتبر المرحلة مكتملة إلا بعد:

- نجاح CI.
- نجاح اختبارات E2E.
- نجاح تطبيق migrations على المشروع الحقيقي.
- نجاح Auth بحسابات حقيقية.
- نجاح RLS لكل دور.
- نجاح دورة طلب حقيقية من الإنشاء حتى التسليم.
- نجاح سيناريوهات Smart Dispatch.
- نجاح الإلغاء وإرجاع المخزون.
- نجاح Edge Function.

الدفع الإلكتروني يبقى مرحلة مستقلة حتى يتم ربط مزود دفع فعلي.
